# KeenDesk — RustDesk Server для Keenetic / Netcraze

**KeenDesk** — русская инструкция и установщик официального **RustDesk Server OSS** для роутеров **Keenetic / Netcraze с Entware и ARM64 (aarch64)**. Сервер работает непосредственно на роутере, без Docker и отдельного компьютера. Клиенты — обычный RustDesk.

Проект автоматизирует установку `hbbs`/`hbbr`, создание ключей, автозапуск, перезапуск после сбоя, ограничение журналов и правила firewall. Это самостоятельная обвязка вокруг официальных бинарников RustDesk, а не Pro-версия и не форк сервера. [Происхождение и лицензии](SOURCE-NOTICE.md).

Подробные разделы: [совместная работа с XKeen](docs/XKEEN.md) · [VPN и KeenDNS](docs/VPN.md) · [обслуживание](docs/OPERATIONS.md) · [похожие решения](docs/ALTERNATIVES.md) · [результаты испытаний](TESTING.md).

## Что нужно заранее

- Keenetic/Netcraze с архитектурой **ARM64**. Проверка в SSH: `uname -m` должен вывести `aarch64` или `arm64`. MIPS/MIPSEL и ARMv7 этой версией **не поддерживаются**.
- Установленный Entware, рабочий `/opt`, SSH-доступ к **Entware от root**. Встроенная командная строка KeeneticOS и Linux-shell Entware — разные среды.
- Постоянный накопитель, желательно ext4; не менее **128 МиБ свободно на `/opt` после установки зависимостей**, лучше 256 МиБ и больше для журналов и копий. Python тоже занимает место.
- Рабочие системные часы, DNS и HTTPS-доступ к GitHub и репозиторию Entware.
- Для обновления — минимум **256 МиБ свободно**; большая база и сохраняемые снимки требуют дополнительного места.
- Доступ обоих клиентов к роутеру: через ZeroTier, SSTP/OpenConnect, локальную сеть или публичный IPv4.
- Поддержка netfilter в ядре. Если нужные модули отсутствуют, установщик не запустит сервер без firewall. Компоненты KeeneticOS устанавливаются через веб-интерфейс; установщик не обновляет прошивку.

На **Keenetic Ultra KN-1811, KeeneticOS 5.1.4, Entware aarch64-k3.10** проверены чистая установка 0.2 с GitHub и последующие обновления до **v0.2.2**: автонастройка ZeroTier/XKeen, новые ключи при переустановке и их сохранение при обновлениях, автозапуск сервера и панели после reboot, TCP/UDP RustDesk и передача через relay. Чистая установка непосредственно 0.2.2 дополнительно проверена в ARM64 VM. Это не обещание совместимости с любым устройством. Подробные результаты и ограничения: [TESTING.md](TESTING.md).

## Установка одной командой

В SSH-shell Entware выполните:

```sh
(set -eu; /opt/bin/opkg update; /opt/bin/opkg install curl ca-bundle; rd_setup="$(mktemp /tmp/rustdesk-install.XXXXXX)"; trap 'rm -f "$rd_setup"' EXIT; curl -fsSL --proto '=https' --tlsv1.2 https://raw.githubusercontent.com/Zhanchuraev/KeenDesk/v0.2.2/install.sh -o "$rd_setup"; /bin/sh "$rd_setup")
```

Команда скачивает завершённый файл и только после успешной загрузки запускает его. Установщик проверяет контрольные суммы своих служебных файлов, скачивает закреплённую версию **RustDesk Server OSS 1.1.16** из официального GitHub Releases, проверяет SHA-256 и тип ARM64 ELF. Глобальный `opkg upgrade` не выполняется.

Если найден **ровно один IPv4-адрес ZeroTier** на интерфейсе `zt…`, он будет выбран автоматически. При неоднозначности или отсутствии ZeroTier установщик спросит адрес и Linux-интерфейсы доступа. Привязку к сети ZeroTier и авторизацию её участников нужно выполнить заранее.

Установщик не создаёт аккаунт ZeroTier, VPN-пользователей, подписки, домены KeenDNS или VPN-серверы. Он настраивает **RustDesk поверх уже работающей сети**. Для каждой установки сервер сам создаёт новую пару ключей: общего ключа для всех пользователей проекта нет.

### Явно заданные параметры

При необходимости можно сначала скачать `install.sh`, а затем передать настройки:

```sh
curl -fsSL https://raw.githubusercontent.com/Zhanchuraev/KeenDesk/v0.2.2/install.sh -o /tmp/rustdesk-entware-install.sh
RD_ADDRESS=10.147.17.1 RD_INTERFACES=zt0 RD_NETWORKS=10.147.17.0/24 /bin/sh /tmp/rustdesk-entware-install.sh
```

**Все IP и интерфейсы в примерах вымышленные: замените их своими.** Адрес выбирается так, чтобы оба клиента могли обращаться к одному серверу. В адресе не нужны `http://`, порт или путь.

| Переменная | Значение |
|---|---|
| `RD_ADDRESS` | IPv4/DNS-имя роутера, которое попадёт в настройки ID и relay |
| `RD_INTERFACES` | Linux-интерфейсы входящего доступа через пробел, например `zt0` или `br0` |
| `RD_NETWORKS` | Допустимые IPv4-подсети **источников** через пробел; пусто — любые источники на указанных интерфейсах |
| `RD_XKEEN` | `auto` по умолчанию; `xkeen` — известная схема обхода; `off` — без специальных DSCP/mark XKeen |

Для шаблона интерфейса, например `ppp+`, обязательна конкретная подсеть VPN. Один только `ppp+` может охватывать и другие PPP-подключения роутера, поэтому установщик не разрешает его без ограничения источников.

Флаг `--check` выполняет предварительные проверки и показывает план без создания серверных служб и правил. Bootstrap при этом всё ещё может установить недостающие зависимости Entware. Если есть старая/чужая установка, проверка остановится с объяснением.

## Что ввести в RustDesk

После установки все значения печатаются в терминале. Показать их повторно:

```sh
rustdeskctl client
```

На **обоих** устройствах: **Настройки → Сеть → ID/Ретранслятор**.

| Поле | Значение |
|---|---|
| Сервер ID | `АДРЕС_РОУТЕРА:21116` |
| Ретранслятор | `АДРЕС_РОУТЕРА:21117` |
| Сервер API | пусто |
| Key | публичный ключ, который вывел установщик |
| Использовать WebSocket | **выключено** |
| Отключить UDP | **выключено** |
| Разрешать небезопасные TLS | **выключено** |

В главном окне подключайтесь к **ID удалённого компьютера**, который показывает RustDesk. Адрес сервера вводится в сетевые настройки, а не вместо ID компьютера. Пароль/подтверждение удалённого доступа задаются на самом удалённом клиенте и не совпадают с серверным публичным ключом.

При работе через VPN оба устройства должны иметь маршрут до `RD_ADDRESS`. Это может быть VPN на каждом компьютере или корректно настроенная маршрутизация через подключённый роутер. Само заполнение полей RustDesk VPN-туннель не создаёт.

Для первой проверки включите на управляющем клиенте постоянное использование ретранслятора, если такая опция доступна. Проверьте экран, управление, передачу файла, простой и повторное подключение. Затем решите, оставлять ли принудительный relay: при разрешённых маршрутах RustDesk может установить прямое соединение между клиентами.

## Если нет белого IP

Это нормальный сценарий: сервер может оставаться за NAT провайдера. Клиентам нужен маршрут к его частному адресу.

| Способ | Нужен белый IP роутера | Использует облако KeenDNS | Что требуется клиентам |
|---|---|---|---|
| ZeroTier | Нет | **Нет**, это отдельная сеть | ZeroTier или маршрут через участника этой сети |
| SSTP-сервер Keenetic | Нет, поддерживается облачный доступ | Да | SSTP-подключение к Keenetic |
| OpenConnect-сервер Keenetic | Нет, поддерживается облачный доступ | Да | OpenConnect/совместимый VPN-клиент |
| Прямой доступ по IPv4 | Да | Можно использовать KeenDNS в **прямом** режиме как DNS-имя | Доступ к портам сервера через Интернет |

SSTP и OpenConnect действительно умеют работать через облако Keenetic при частных IP. Это подтверждено в документации [SSTP](https://support.keenetic.ua/titan/kn-1811/en/19090-sstp-vpn-server.html) и [OpenConnect](https://support.keenetic.com/hero/kn-1011/en/38655-openconnect-vpn-server.html). Скорость такого VPN зависит в том числе от облачного транспорта.

Здесь KeenDNS переносит **VPN-туннель**, а обычный TCP/UDP RustDesk идёт **внутри** него. Это отличается от публикации RustDesk как веб-приложения в KeenDNS. Для описанного варианта не нужны Pro, WebSocket, nginx или HTTP-публикация портов 21116/21117.

Пошаговые варианты, маршруты и правила доступа: **[docs/VPN.md](docs/VPN.md)**.

## Переустановка и обновление 0.2 на реальном Keenetic

28 сентября 2026 на **Keenetic Ultra KN-1811, KeeneticOS 5.1.4, Entware aarch64-k3.10** удалена предыдущая установка 0.1.0. До новой установки подтверждены отсутствие девяти рабочих путей сервера и его цепочек firewall. Закрытая копия для восстановления вынесена с роутера; старая пара ключей в новую установку не возвращалась.

С опубликованного GitHub-тега v0.2.0 выполнена чистая установка с проверкой контрольных сумм bootstrap. ZeroTier и режим XKeen определились автоматически, созданы новые ключи. С отдельного компьютера проверены TCP NAT, UDP-регистрация/heartbeat, адрес relay, отказ с неверным ключом, две relay-сессии с 1 МиБ суммарно и SHA-256; WS-порты через ZeroTier закрыты. Синтетическая запись теста затем удалена.

На том же роутере выполнены настоящие команды `rustdeskctl update --version v0.2.1` и затем `rustdeskctl update --version v0.2.2`: файлы получены с GitHub, сохранены новые ключи, созданы снимки для отката, проверки TCP/UDP/relay прошли. Это отдельное испытание самой команды загрузки обновления, дополнительно к переходу с 0.1.0 в ARM64 CI.

Живые испытания выявили две особенности, исправленные в стабильном 0.2.2: Python-панель на процессоре роутера могла не уложиться в 500 мс; при reboot Entware стартовал до появления адреса ZeroTier. Теперь готовность процесса ожидается до 10 секунд, а supervisor повторяет запуск отсутствующей панели после появления VPN.

После отдельной полной перезагрузки с 0.2.2 **сервер и панель запустились автоматически, без ручного `start`**. В журнале зафиксировано ожидание VPN и успешное снятие этого ожидания. Все десять проверок `doctor` прошли; TCP/UDP и relay дополнительно проверены с отдельного компьютера. Панель отвечает HTTP 200, API без ключа — 401. Тринадцать установленных служебных файлов совпали с SHA-256 релиза, загрузочный обработчик — с кодом восстановления; ключи сохранились. HTTP-интерфейс Keenetic, локальный DNS и HTTPS через Xray работают, контрольные суммы шести конфигураций Xray и его init-скрипта не изменились.

Ручной и автоматический откат, прерывание обновления и лимит пяти падений испытаны в ARM64 CI. На физическом роутере искусственное повреждение обновления и многократные падения не воспроизводились. Реальный GUI-сеанс двух клиентов по-прежнему требует отдельной проверки пользователем.

## Испытания предыдущей версии 0.1.0 на реальном Keenetic

**28 сентября 2026 выполнена чистая установка именно GitHub-релиза `v0.1.0`** на Keenetic Ultra KN-1811, KeeneticOS 5.1.4, Linux 4.9, Entware aarch64-k3.10. Предыдущая ручная установка была удалена: бинарники, ключи, база, журналы, автозапуск, hooks, старые архивы и собственные правила. Копия для отката была заранее вынесена с роутера. Перед установкой подтверждены отсутствие старых файлов/правил и свободные серверные порты.

Выполнена ровно команда из README, с загрузкой `install.sh` и служебных файлов с GitHub. Без ручной правки конфигурации определились интерфейс/адрес ZeroTier и известная схема XKeen. Сервер создал новую пару ключей. Семь установленных служебных файлов совпали по SHA-256 с релизом; процессы работали с UID/GID 21116, каталог данных имел права `700`, приватный ключ — `600`.

До и после **одной полной перезагрузки** проверены TCP 21115/21116, UDP-регистрация, heartbeat, выдача адреса relay, отказ с неверным ключом и две relay-сессии по 1 МиБ суммарно на каждую серию, с совпадением SHA-256. WS-порты 21118/21119 оставались недоступны через ZeroTier. Принудительно завершённый `hbbr` восстановился за 5,5 секунды.

Автозапуск после reboot выполнен без ручного `start`. Во время загрузки Keenetic пересоздавал firewall: supervisor зарегистрировал временные ошибки, остановил дочерние процессы и сам восстановил их после готовности правил. После загрузки ключи и служебные файлы сохранились. Веб-интерфейс по HTTP/HTTPS, локальный DNS и HTTPS через Xray прошли проверку; контрольные суммы шести конфигураций Xray и его init-скрипта не изменились.

Дополнительно проверена relay-сессия: 4 МиБ переданы до интервала в 70 секунд, ещё 4 МиБ после него, SHA-256 совпал. В течение интервала каждые 10 секунд выполнялся короткий двусторонний обмен. Полностью молчащий сырой relay-сеанс в отдельном опыте закрылся примерно через 33 секунды: это соответствует таймауту отсутствия данных более 30 секунд в официальном `hbbr` 1.1.16, а не перезапуску службы. Подробнее — [проверка длительного соединения](docs/OPERATIONS.md#проверка-длительного-соединения).

После тестов удалены только две синтетические записи регистрации; остальные записи клиентов сохранены. Финальный обмен 512 КиБ через relay и проверки TCP/UDP прошли успешно.

Это проверка конкретной модели и версии, а не гарантия для всех Keenetic. Реальный GUI-сеанс с изображением рабочего стола пользователь проверяет отдельно; протокольные тесты его не подменяют. Личные адреса, ключи, база и журналы роутера в этот репозиторий не включены.

## Автоматические проверки репозитория

[GitHub Actions](https://github.com/Zhanchuraev/KeenDesk/actions/workflows/checks.yml) показывает фактический результат для каждого коммита.

- Unit-тесты проверяют параметры, ограничения VPN-шаблонов, отказ от перезаписи чужой установки, SHA-256, состав ZIP и статический ARM64 ELF, изоляцию собственных цепочек firewall и воспроизводимость bootstrap.
- Проверяется синтаксис Python и shell.
- На отдельной виртуальной машине `ubuntu-24.04-arm` выполняется чистая установка настоящих официальных ARM64-бинарников. `iptables`, процессы, файловые права и отдельное сетевое пространство клиента настоящие. Пути Entware, `opkg` и наличие `ndmc` имитируются: этот тест не проверяет установку пакетов Entware и события самой KeeneticOS.
- Протокольный клиент проверяет TCP NAT, UDP-регистрацию и heartbeat, объявленный адрес relay, отказ с неверным ключом, две relay-сессии с передачей 1 МиБ суммарно в обе стороны и блокировку WS-портов.
- Проверяются повторная установка с сохранением ключа, восстановление убитого `hbbr`, вызов netfilter-hook, повторное применение правил, изменение настроек, резервная копия и полное удаление с сохранением ключа в закрытом архиве и сохранением чужого правила firewall.

Интеграционные тесты предназначены только для одноразовой VM GitHub Actions. Не запускайте `tests/integration_ci.py` на рабочем роутере.

## Что нужно проверить на своём устройстве

1. Чистая установка на конкретной модели и текущей версии Entware.
2. Реальный сеанс двух клиентов RustDesk: экран, управление, передача файла, простой и повторное подключение. Проверка протокола не заменяет GUI-сеанс.
3. Автозапуск после перезагрузки и восстановление после переподключения VPN.
4. Сохранность других сервисов роутера и фактический сетевой путь при XKeen.
